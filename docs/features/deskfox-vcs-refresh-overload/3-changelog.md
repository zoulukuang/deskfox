# Git 差异刷新占满本地连接

2026-11-11，Windows 电脑。2026.12.1 的现场网络日志记录了同一项目 1,300 多次差异请求，目录树和回答提交等待连接超过 8 分钟。连续文件事件反复使差异查询失效，查询层取消旧结果后，已发出的 HTTP 请求仍在等待。

保留 100 毫秒防抖。差异请求进行中时合并后续刷新，响应结束后再发一次。会话切换工作区或分支时丢弃旧查询键的待刷新。复现用例用同一组文件事件比较修复前后的并发数，并检查目录展开和回答提交。

Windows 电脑在生产前端构建上对照验证。第一条差异响应挂起时，旧构建发出 9 条请求，修复后只发出 1 条，响应释放后补刷 1 条。等待期间目录可展开，回答提交返回成功。生产构建的 4 条相关 Playwright 用例、app 1,197 条单测和 41 条浏览器测试、app 与 e2e 类型检查均通过。正式 Windows 安装版待随发布流程验证。

2026-11-11，Windows 电脑从 `8d979a0a9b` 构建并启动了独立 local 包。用该包的 Windows 后台和生产前端在临时 Git 仓重放 12 次对 Git 忽略目录的快照替换。差异请求挂起时只发出 1 条，期间文件树展开约 100 毫秒，释放后补刷 1 条。带调试端口的启动被自动审批拦截，生产前端在独立 Chromium 中完成负载测试。正式版复发日志仍来自原 2026.12.1 进程，记录了同项目 2,127 条差异请求。

### 两端对比与结论边界

Windows 已由现场网络日志和对照验证确认 Git 差异刷新请求积压。macOS 同样具备「高频文件变化、重开恢复、后台未异常退出」特征，因此高度怀疑同一机制，但缺少 macOS 请求排队现场，尚不能写成两端根因完全一致。后台仍可运行不代表前端连接未堵塞，健康检查也不能替代用户请求可用性检查。

另发现一条独立的文件树刷新路径：`packages/app/src/context/file.tsx` 的 `refreshDir` 使用 `force: true`，`file/tree-store.ts` 的强制刷新绕过 inflight 去重。Windows 已修的是 `pages/session.tsx` 的 Git 差异刷新，不是此目录列表路径；不要将两者混称为同一处修复，也不要在缺现场证据时扩展修复范围。此前找到的 2026-07-28 Windows 渲染进程 OOM 属另一事件，不作为本次同因依据。

## FoxTake 实际副本串行计时（笑南的电脑，2026-11-13）

按李哲转来的脚本，在 `/Volumes/ExtSSD/My-Apps/foxtake` 的实际工作副本计时三轮，不创建合成文件，不修改、暂存或清理项目文件。Git 参数包含 `--no-optional-locks` 及指定的五项 `core.*` 临时配置；两项已跟踪统计与 status 并行，之后完整已跟踪 diff，再逐个未跟踪文件串行执行 numstat 与完整 diff。HEAD 为 `350f8244`，14:35 的原始命令统计为 186 个未跟踪文件，14:43:45 复核仍为 186；测后暂存差异为空，原有工作区差异仍为 1 文件、12 行新增。

脚本的首次三轮输出均为 1 个未跟踪文件、约 0.1 秒，**这组无效，不计入性能结果**。复核发现未跟踪文件中存在字面文件名 `-`，Git 将其当 stdin，读取了 here-string 中余下的文件列表。仅将循环的两处文件参数从 `"$f"` 改为 `"./$f"`，避免该特殊解释，再重新测三轮；其余 Git 参数和调用顺序未变。临时脚本位于 `/tmp/vcs-diff-timing.sh`，没有修改产品代码。

| --- | --- | --- | --- | --- |
| 1 | 186 | 0.09 秒 | 4.91 秒 | 5.00 秒 |
| 2 | 186 | 0.06 秒 | 4.40 秒 | 4.46 秒 |
| 3 | 186 | 0.08 秒 | 4.63 秒 | 4.71 秒 |

与上午现场 6.732 秒的发送至响应头时间相比，当前串行脚本均值约为七成，不是李哲机器上合成小文件实验的四成。但脚本没有覆盖完整 HTTP 接口、运行时调度及响应序列化/压缩，且不是上午同一时刻的资源状态，不能将剩余约 2 秒全部归因于并发争用，也不能仅靠跨机器比较区分文件大小与机器环境的影响。Git 差异请求积压和其他请求排队已经由 NetLog 独立证明；并发对单请求耗时额外放大多少，仍未定量验证。本轮只测量和补记，不修改忽略规则、不清理未跟踪文件、不发布修复。

### 本轮收口

- **已证实一：请求积压。** 重复 Git 差异请求争用本地连接，导致目录树、状态查询等排队；Mac NetLog 与 Windows 现场吻合，不能再归为后台进程崩溃。

## 源头追查（李哲的电脑，2026-11-13）

本轮只读代码，并在临时目录建合成仓库实验，不改产品代码，不碰正式版数据。代码位置均以本分支为准。

### 源头一：触发放大

- 桌面端启动后台时设 `OPENCODE_EXPERIMENTAL_FILEWATCHER=true`（`packages/desktop/src/main/server.ts:64`，上游代码，非 fork 改动），后台因此监听整个工作区。
- 监听的忽略规则只有 `packages/core/src/filesystem/ignore.ts` 的内置名单，加配置里的 `watcher.ignore`，不读项目 `.gitignore`。Git 忽略目录里的每次变动都会推成 `file.watcher.updated`，前端每收到一条就触发一次差异刷新，尽管这些变动不可能改变差异结果。Windows 复现用的就是这种场景。
- 前端 `pages/session.tsx` 的 `file.startsWith(".git/")` 过滤对后台推来的绝对路径永远不生效。目前后台在 `.git` 内只监听 `HEAD`，实际影响小。

### 源头二：单次差异计算按未跟踪文件数线性变慢

- `packages/opencode/src/project/vcs.ts` 先用 `git status --untracked-files=all` 把未跟踪目录展开成文件，再对每个未跟踪文件串行调用 `statUntracked` 与 `patchUntracked`（`packages/opencode/src/git/index.ts`），也就是每个文件起两个 git 进程。
- 合成仓库（小文件，本机 Mac）实测：50 个 0.85 秒，186 个约 2.7 至 2.9 秒，200 个 3.6 秒，800 个 13.7 秒，约每个文件 15 至 17 毫秒。笑南真实副本 186 个约 4.65 秒（见上节），量级一致；真实文件更大，比合成实验更慢。
- 两个源头相互放大：触发多，乘以单次慢，就把 Chromium 每个来源 6 个连接占满。本分支已有修复只封住了积压，两个源头都还在。
