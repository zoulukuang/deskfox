## 元原则(对齐 CLAUDE.md)

**稳定 > 简洁 > 一切**。测试纪律服务于三件事:
1. 跟随上游 opencode 升级时**不破坏 fork 自家的 feature**
2. 满足自有开发需要,**新 feat 不破老 feat**
3. **维护成本最低** — 测试本身要便宜,flaky 测试要立刻清除

**绝对单一**:一套测试纪律 / 一套金字塔比例 / 一种"测试通过"标准。**不分层、不双套、不双轨**。

## 五条核心决策(已固化)

### 决策 1:新 feat 必须含至少 1 个测试(R5 硬约束)

**规则**:任何引入用户可见行为或核心逻辑的 feat,**必须**至少含 1 个 e2e 或 unit 测试。pre-push hook 守门(后续接入)。

**例外清单**(以下不强制):
- **Tiny 改动 < 50 行**(纯 bug fix / 文案 / 配置 — 维度过窄,测试成本 > 收益)
- **docs / 规范文档 / 注释**(没法测)
- **品牌资源 / icon / 字体**(纯静态)
- **基础设施 / build 脚本 / CI workflow**(走"实跑通过"验证,不要求单元测试)
- **R3 配置 override**(`electron-builder.deskfox.config.ts` / `branding/theme.css` CSS 变量)
- **上游 sync merge commits**(变更非 fork 自家,延用上游测试)

**判定权**:Claude 自判,边界模糊时主动问 user。

**规模分级 vs 测试要求**(v4,2026-05-23 升级 — Phase 1 mock e2e 基础设施落地后):

| 规模 | 行数 | 测试要求 |
|---|---|---|
| **Tiny** | < 50 | 不强制(但鼓励);如有验证点,changelog 简述即可 |
| **Medium** | 50-500 | **spec 必含「测试用例清单」(R8)** + **≥ 1 Phase 1 e2e happy path**(无 e2e 不算交付) |
| **Large** | > 500 / 触动 ≥ 5 上游文件 | **spec 必含「测试用例清单」(R8)** + **≥ 2 Phase 1 e2e + 5 个 unit** |

**R8 测试用例清单(2026-06-01 立)**:Medium+ 的 `1-spec.md` 必须在「测试覆盖范围」段下列出**逐条可勾选的测试用例**(每条:验什么 / 用什么层级测 unit·Phase1·Phase2·CDP / 预期),**写代码前就定好**。开发完成按此清单逐条跑、全绿,才进 merge 流程(见操作流程 R9)。理由:把验证范围在动工前固定下来,避免"做完才发现漏测"(2026-06-01 catalog 抽取后才发现标签不一致即此教训)。运行时/native 风险点(数据加载、native dialog、跨进程)必须显式列入,不能默认"unit 过了就行"(对照 [CDP 自测 ≠ 真桌面 QA])。

**Phase 1 e2e** = 中层 mock e2e(`packages/app/e2e/*.spec.ts` 用 `bootstrapMock` + fixture helpers,2-3s/case,<2 min 全套)。参 `docs/features/e2e-phase1-mock-mode/`。

### 决策 2:关键模块**双清单**(2026-05-07 修订 v2 — 选项 C)

**规则升级**:从单一"关键模块清单"拆成 **Logic 清单 + View 清单** 双清单,各自门槛。

**为什么改**:首版规则用"文件级行覆盖率 ≥ 80%"统一门槛,实际测试时发现 SolidJS 组件文件(JSX 大部分声明式)用 unit 测无意义。D 系列实施后(D1-D4)证实"helper extract from component"模式可行,view layer 应当走 e2e。把这条结构性区分写进规则,长期防止"组件文件覆盖率永远低 + view layer 永远不被 e2e 覆盖"双重空白。

#### Logic 清单(单元测覆盖率 ≥ 80% 行)

**适用文件类型**:纯 logic 文件 — utility / pure helper / 计算函数 / 数据 dict / 协议层
**门槛**:**单元测试行覆盖率 ≥ 80%**(`bun test --coverage`)
**清单**:

| 文件 | 当前覆盖率 | 进入清单时间 |
|---|---|---|
| `packages/app/src/utils/md-export-docx.ts` | **~100%** ✅ | v1(2026-05-07)|
| `packages/app/src/utils/markdown-editor-extensions.ts` | ~75% ⚠ | v1(2026-05-07)|
| `packages/desktop/src/main/deskfox/db-schema-guard.ts` | **100%** ✅ | v8(2026-08-18,user 拍板)|

> **`db-schema-guard.ts` 进清单的理由**(REQ-084①):它是「这个 db 的 schema 是不是比本内核超前」的
> 唯一判定点,**判错的代价是用户数据被误隔离**(判 ahead → 库被改名挪走、以空库启动)。
> 判定规则本身还带两个易错边界:只认 `^\d{14}_` 时间戳形态 id、legacy 名一律忽略;读不出一律 fail-open。
> 这类「一个纯函数守着不可逆动作」的文件正是 Logic 清单要长期钉住的类型。
> 同族的 `db-schema-guard-io.ts`(83.9%)/ `db-schema-startup-check.ts`(94.1%)/
> `app/src/utils/db-quarantine-notice.ts`(100%)当前也都在 80% 以上,但它们含 IO / 接线,
> 不算纯 logic,**不入清单**(变动时顺带看一眼覆盖率即可)。

**进入条件**:任一新文件作为 Logic 模块上线时,**user 拍板**才能加;清单内文件必维持 80% 行覆盖。

#### View 清单(e2e 必测路径,每文件 ≥ 1 happy path)

**适用文件类型**:SolidJS 组件文件(.tsx) / 用户高频接触的 view layer
**门槛**:**至少 1 个 e2e happy path 测试 + 关键交互 e2e 路径**(覆盖该文件实际暴露的用户行为)
**清单**:

| 文件 | 必测 e2e 路径 | 当前状态 | 进入清单时间 |
|---|---|---|---|
| `packages/app/src/components/dialog-settings.tsx` | "切语言看版本牌正确"+"打开关闭设置面板" | 🔴 **硬门槛生效(v4)** — 需补 | v2(2026-05-07)|
| `packages/app/src/pages/session/file-tabs.tsx` | "选 .md → 右键菜单 4 项显示"+"切 tab 标题更新"+"无选区右键 disabled 状态" | 🔴 **硬门槛生效(v4)** — 需补 | v2(2026-05-07)|

**进入条件**:任一新组件文件作为 View 模块上线时,**user 拍板**才能加;清单内文件必带至少 1 个 e2e。

**View 清单的 trigger 效应**:**View 清单第 1 个文件加入时,必须先解决 e2e 基础设施 setup**(opencode sidecar 或前端 mock mode `VITE_E2E_MOCK=1`)。否则清单只是空话。当前 2 个文件已加,但 e2e 基础设施 setup 是该清单的**前置依赖**,启动时机 user 单独决定。

#### 双清单的关系

```
Logic 清单(单元测,行覆盖)              View 清单(e2e,行为覆盖)
       ↓                                       ↓
  pure helper / 工具函数                  SolidJS 组件 / view layer
  改动频繁的边界 case                      用户高频交互路径
       ↓                                       ↓
  bun test --coverage                     Playwright + chromium
       ↓                                       ↓
  CI 每次 PR 跑(快)                     CI 关键路径跑(慢)
```

**helper extract 模式得到正式承认**:把组件内的纯计算抽到独立 helper 文件,该 helper 进 Logic 清单(行覆盖)+ 原组件进 View 清单(e2e)。这是 D1 / D2 实施验证过的有效模式,正式进规则。

#### 清单维护

- **加入双清单**:user 拍板;清单条目要标"进入清单时间"+"理由"
- **移出双清单**:该文件已退役 / 重构拆分,Claude 提议 + user 同意
- **每季度复核**:覆盖率(Logic)+ e2e 通过率(View)— 2026 Q3 第一次复核
- **跨清单移动**:组件 helper extract 后,原组件留 View 清单,新 helper 进 Logic 清单

**例外**:
- 仅 import 第三方库的胶水代码(< 20 行)不强制覆盖
- 上游同步过来的文件(非 fork 自家维护)不强制
- ~~View 清单文件**等 e2e 基础设施就绪后**才生效硬门槛~~ — **v4 升级:Phase 1 mock e2e 基础设施已落地(`docs/features/e2e-phase1-mock-mode/`),View 清单硬门槛即时生效;清单内文件未补 e2e 视为治理 debt,新 feat 触动这些文件时一并补**



### 决策 3:测试数量比例 70 / 20 / 10(unit / integration / e2e)

**规则**:全仓测试数量分布按行业经验维持 70 / 20 / 10。**Claude 写新测试时优先写 unit,e2e 只用于"用户视角的端到端验证"**。

```
1000 个测试时:    700 unit + 200 integration + 100 e2e
今天起步阶段:     先扩 unit 到 800+,e2e 慢慢补,达成比例靠时间
```

**比例失衡处理**:
- 当 e2e 数量 > 总测试 15% → 触发警告,review 是否 e2e 过度堆叠(高维度问题向 unit 下沉)
- 当 unit 数量 < 总测试 60% → 触发警告,补 unit

**自动化测试 ≠ Playwright e2e** — 这条规则的核心是"**测试金字塔比例,而不是 e2e 数量本身**"。

### 决策 4:修 bug 必须先写复现测试(R7 硬约束)

**规则**(v4,2026-05-23 升级):任何 bug fix 都**必须先写一个能复现该 bug 的测试**(测试此时 fail),然后修代码使测试 pass。**bug-repro 测试默认为 Phase 1 e2e**(覆盖 reactive 层 / 跨组件场景,不再止于 unit DOM event 假设)。fix commit 与测试代码必须**同一笔 commit**。

**为什么 v4 提级 e2e**:v3 多笔 bug-repro 仅到 unit 层(如 `chat-drop-overlay-stuck-fix` 用 DOM event 单测),`auto-save-debounce-flush` 那晚 3 round-trip 暴露 — reactive 层 bug 单测假设错就漏。Phase 1 e2e 端到端跑 user flow,reactive 链真触发,catch 率高得多。

**为什么强制**:
- 防止同一 bug 几个月后又冒出来重修
- 自然增长测试覆盖率(不需要"为了写测试而写测试")
- review 时 "测试 + fix" 一起读,意图清晰

**例外**(以下情况测试可省):
- **bug 在外部依赖**(上游 / 第三方库)— 我们只能 workaround,不便测试上游行为
- **bug 仅在特殊环境复现**(某 user 特定 OS 配置 / 特殊文件锁状态)
- **修文案 / 翻译错误**

**操作流程**:

```
1. 收到 bug 报告
2. 写一个测试,能在当前代码下 fail(复现 bug)
3. 改代码使测试 pass
4. 同一 commit 提交测试 + fix
5. commit message 注明 [bug-repro: <一句话>]
```

**举例**(假想):今天的 `right-click-stale-selection-fix` 如果在新规范下做,流程会是:
```
step 1: 写 e2e 测试 "选 A → 点空白 → 别处右键不命中 A"(此时 fail)
step 2: 改 file-tabs.tsx 加 handleLightDomContextMenu
step 3: 测试 pass,commit 包含测试 + 修复
```

### 决策 5:测试代码 review 责任 — Claude 自审起步

**规则**:Claude 写完测试后,**用同一会话的另一轮调用做自审**,检查:
- 测试是否真的能抓出 bug(不是只 assert "字符串非空"之类的 trivial 检查)
- 测试是否有 race condition / time-dependent flakiness 风险
- 测试是否依赖外部资源(网络 / 文件系统状态 / 真实 LLM API)— 应当用 mock 替代

**自审形式**:
- 单测:Claude 提出"如果代码改成 X,这个测试还能 fail 吗?"逐条检查
- e2e:Claude 检查 selector 稳定性 / await 时机 / 失败诊断信息

**升级路径**(后期):
- **Phase A(现在)**:Claude 自审 + user 抽查
- **Phase B(未来)**:接入 mutation testing(故意改坏代码自动验证测试能不能抓到)
- **Phase C(可选)**:接入第三方人工 reviewer

## 操作流程

### 写新 feat 时

```
1. 写 feat spec(docs/features/<id>/1-spec.md)— Medium+ spec 必含「测试用例清单」(R8):
   动工前就把"验什么 / 哪个层级测 / 预期"逐条列好,运行时/native 风险点显式列入
2. 写代码实现
3. 写测试(unit 优先 / e2e 仅用于用户级验证)— 覆盖 R8 清单每一条
4. 【R9 分支内验收闸】按 R8 用例清单逐条跑 + 旧测试(防回归)全套,全绿;
   有问题就在 feat 分支内解决干净,绝不带病进 merge 流程
5. 全绿 → commit(代码 + 测试同一 commit)→ push feat 分支(私有 work,可自主)
6. 【三铁律】请示 user → user 授权 → merge 到 main(--no-ff)
7. 【三铁律】请示 user → user 授权 → push main → 双远端
8. feat 分支销毁(一次性容器)
```

> **R9 分支内验收闸(2026-06-01 立)**:开发完成后,必须按 R8 用例清单跑全套测试(unit + 相关 e2e)+ 全绿,**才向 user 提"是否 merge"**。问题必须在 feat 分支阶段解决,不把已知问题带过 merge 线。
> **自动 backstop**:`pre-push` hook 跑 typecheck(fork 范围,排除 §七 console)+ fork 自家包单元测试(media-gen / adapter-feishu-lark / app),red 则拦 push。这是兜底,主闸是上面的人工+按清单验收。
> **electron 仓口径(v6 2026-06-15)**:换基座仓主开发分支是 `feat/electron-replatform`(非 main),故单测 backstop 改为**每次 push 都跑**(原 Tauri 仓"仅 push 含 main"在此等于不跑);详见修订记录 v6。
> **注**:步骤 6/7 受三铁律约束 —— merge 与 push **各需 user 单独授权**,不是自动一气呵成(本流程旧版"ff merge dev → push"已废,2026-05-21 main 改名 + 三铁律后口径以此为准)。
>
> **verify:deskfox — DeskFox 验收链铁律(2026-06-15 立)**:DeskFox 任何改动(UI / 查看器 / 供应商 / 设置 / 启动·主进程)**完成后、向 user 提 merge 前**,必须跑 `bun run packages/branding/smoke/verify.ts --changed`(或 `--scope ui|provider|viewer|all` / `--only <probe>`)并**把判定贴出来**。这是 R9 里 View/CDP 那部分的标准自动跑法(L0 `typecheck`+`lint` → L2 连 dev CDP 9222 跑 `smoke.py` 相关 probe),**不替代** R8 清单里的 unit 测试(unit 照决策 1/2 跑)。
> - **判定即闸**:🔴(crash 或 L0 不过)= **绝不说"完成"、绝不进 merge 流程**;🟡(fail:渲染空白 / console.error / 弹窗没开)= 必须 user 看过并确认可接受才往下走;🟢 = 放行。退出码 **1/2/0 对应 🔴/🟡/🟢**,可直接挂 CI / ship 闸。
> - 编排器 `packages/branding/smoke/verify.ts`;自动探活 9222 复用在跑的 dev(没起就后台拉、跑完只杀自己拉起的那个),复用现有 dev 时自动剔 boot 免 reload 打断会话。
> - **改启动链 / 主进程 / 插件注入时(L1 冷启动)**:`bun run packages/branding/smoke/verify.ts --cold` —— 杀全部进程→**真冷启**→冷启动健康监控 ~22s,抓 **sidecar 预热竞态**(首个 file.list 500 / connection-refused 弹红 toast,reload/暖态永远测不到)。脚本 `cold-start.py` 自包含入仓(源 OPENCODE-PLAN 诊断工具),**已修 conn-refused 误报**(终态已连上才算预热瞬时,否则=sidecar 没起来真 FAIL,保留真检出)。判定 🟢0/🔴1(无 🟡)。
> - **发版前(L3 发布物)**:`bun run packages/branding/smoke/verify.ts --release`(或 `--build` 先打包再校验)校验 `dist-deskfox` 产物 —— 安装包存在 / **latest.yml 的 sha512 与 exe 实算一致(electron 自动升级命门,不一致=客户端下载后校验失败装不上)** / 版本号非 0.0.0 / `.blockmap` / LibreOffice 进包;任一不过即 🔴,**绝不发布**。这是 dev 态 L0/L2 测不到、只有真打成安装包才暴露的一类。`/ship` 已含大半,此为可独立重跑的产物判定。**electron-updater 口径**(`*.exe`+`latest.yml`+`.blockmap`),不复用已随换基座过时的 Tauri 版 `verify-updater-artifacts.ts`(那份查 `*-setup.exe`+`.sig`)。

### 修 bug 时

```
1. 收到 bug → 复现
2. 写测试(能在当前代码下 fail)
3. 改代码 → 测试 pass
4. commit:测试 + fix 一起,message 注明 [bug-repro]
5. 【R9】跑全套绿 → push feat 分支 →(三铁律:请示授权)merge main →(再请示授权)push 双远端 → 销毁分支
```

### 测试 flaky(偶尔 fail)处理

**绝不能**用 `retries: 3` 一键掩盖。flaky 测试是规范的天敌 — 1 个不稳定测试会破坏整套信任。

**正确流程**:
1. 立即标记 `test.fixme()` 或 `test.skip()` 让 CI 不阻塞 —
2. **同一笔 commit** 加 TODO comment 写明 "为什么 flaky"
3. **48 小时内**修复或移除 — 不能让 skip 测试在仓里堆积
4. 修复方案不是 "retry" 而是定位 race / time-dependence 根因

## performance 组的归属:**进发版验收,不进 pre-push**(2026-08-18 立,REQ-117 收口)

> **为什么要单独写一条**:`packages/app/e2e/performance/` 这一组(时间线基准 + 视觉稳定性)默认被主
> config `testIgnore: "performance/**"` 排除,pre-push 也不跑 —— 于是它坏了半年没人知道
> (2026-08-18 接手时 6 条红 + 脚本本身跑不通)。**没有归属的测试等于没有测试**,所以必须显式钉死它属于哪一档。

**两个套件、一条命令**:

| 套件 | 位置 | 测什么 |
|---|---|---|
| 时间线基准 | `e2e/performance/timeline/*.spec.ts` | 冷/热切会话、首屏、review 面板等的里程碑耗时(输出 `BENCHMARK` JSON 行) |
| 视觉稳定性 | `e2e/performance/timeline-stability/*.spec.ts` | 不变量:区域不重挂载 / 不闪 / 不逆向位移 / 顺序不乱 |

- **跑法**:`bun run --cwd packages/app test:bench`(= performance 单测 + 上面两套 Playwright,自有 config 已是 `workers: 1`)。
  单跑稳定性子集用 `test:stability`,范围被 `test:bench` 完全覆盖。
- **不进 pre-push**:全套分钟级,且基准数值对机器负载敏感 —— 放进 push 闸只会制造噪声,
  逼人 `--no-verify`,反而毁掉现有闸的可信度。
- **进发版验收**:**ship 前必须跑一轮全绿**(与 typecheck / 六包单测 / 默认 Playwright 套件同级)。
  红了先分诊:**基准数值漂移**(机器负载/环境)还是**不变量被破**(真回归)—— 后者一律按 R9 在分支内解决,不带病发版。
- **踩过的坑(别再踩)**:
  1. Playwright 默认 `testMatch` 会连 `*.test.ts` 一起收,把 `timeline-stability/fixture.test.ts`(bun 单测)喂给 Node ESM loader → `Received protocol 'bun:'`,整段一条用例都跑不起来。**修法落在 `test:bench` 脚本的位置参数 `"\.spec\.ts$"` 上,不是改 config** —— `e2e/performance/playwright.config.ts` 命中 pre-commit 黑名单的 `*.config.{ts,js,mjs}`(该规则本意护构建配置,e2e 测试 config 属误伤),不值得为它烧 R4 override 配额。**所以直接跑 `playwright test --config e2e/performance/playwright.config.ts` 仍会撞这个错,请走 `bun run test:bench`。**
  2. e2e 布局基线是**经典布局**(`mock-server.ts` 会种 `newLayoutDesigns: false`)。要测新布局的用例必须自己 `installTimelineSettings`,**且 URL 形状要跟着换**(新布局 `/server/<key>/session/<id>` ↔ 经典 `/<dir>/session/<id>`)—— 用错形状的表现是"冷启动超时",极易被误诊成性能问题。
  3. 视觉不变量要放宽(`stable.maxRemounts` / `continuity.maxGapFrames`)**必须先拿探针实测**(不同 `cpuRate` 各测一轮),并把数据写在用例注释里。**不许直接删断言**。

## 失败处理 — "测试 fail 怎么办"

**绝对不允许**的处理方式:
- ❌ 注释掉 fail 测试
- ❌ 改 assert 让它 pass
- ❌ 加 retries 掩盖
- ❌ 用 `test.skip()` 但不修

**正确流程**:
1. 跑 fail 测试本地复现
2. **判断是 fix bug 还是 fix 测试**
   - 如果是代码出 bug → 走"修 bug"流程(决策 4)
   - 如果是测试本身写错(过严 / 过松 / 假阳性)→ 修测试,commit message 注明 `[fix-test]`
3. **绝不接受**"它有时 pass 有时 fail" — 这是 flaky,走上面 flaky 处理流程

## 与现有规范的边界

- **R1 三级跳决策**(新文件优先)— 不变。新增测试文件天然是新文件,不冲突
- **R2 FORK marker** — 测试文件全是 fork-only,不强制 marker
- **R3 hardcode 禁令** — 测试 fixture 数据可以 hardcode(测试场景需稳定)
- **R4 黑名单 override** — 测试文件不在黑名单,无配额消耗
- **改动规模分级**(Tiny / Medium / Large)— 不变,但本规范的"测试要求"叠加在原分级之上
