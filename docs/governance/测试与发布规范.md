> **性质**:发版正本。版本号 / 渠道 / 打包命令的正本仍是 [`版本号与发布渠道规范.md`](./版本号与发布渠道规范.md),开发期测试纪律(R5 / R8 / R9 / pre-push)的正本仍是 [`自动化测试规范.md`](./自动化测试规范.md),三人分工与回执格式的正本是 `三端协作-Agent接入.md`。**本文只回答一件事:一次发版从哪里开始、过几道门、谁签字、证据放哪、怎么回退。** 不重复上面三份的内容。

## 零、为什么要这份:2026.12.0 的五个教训

2026.12.0(Mac 10-21 / Windows 10-20 发布,11-03 官网回退到 11.2 / 11.1)不是打包出错,是**流程缺门**。逐条事实:

| # | 发生了什么 | 缺的是哪道门 |
|---|---|---|
| 1 | `attachment-cost-guard` 以 **in-progress** 状态进包(INDEX 当时写「Mac 由同事内测」),拖放 / PDF / 大文本行为相对 11.2 变了,用户感知为「功能缺失」 | **候选冻结**:没有「只有 done 的 feat 进包」这条规则 |
| 2 | 改动把 `routeExternalDrop` 收窄、服务端截断 50 KiB、删除文件名合成,**没有任何一条验收项写「与上一正式版行为一致」**;测试被改写成匹配新行为而不是当回归处理 | **行为对照 + 测试删改审计** |
| 3 | 发布动作一次做完:GitHub Release、更新清单、官网链接同时切;出问题后只能官网回退(`deskfox-web` 10d9a10),已升级用户因 updater 禁降级**不能回退**,李哲本机回装 11.2 时正式库被隔离改名 | **分级放行 + 回退预案** |
| 4 | 发版门散在五处:版本号规范 §5(命令还是 Tauri 时代)、自动化测试规范(performance 组、`verify --release`)、CLAUDE.md 验证约定、各发版 feat 目录、以及 **gitignore 的本机文件 `.claude/commands/ship.md`**——协作方根本看不到 | **单一正本** |
| 5 | 12.1 用 11.2 的树替换式合并建候选,把 12.0 的两条发布台账和两个 feat 目录从树里删掉了,事后由 Windows 电脑发现才补回 | **台账只追加** |

做对了的部分不改:local 第 4 档隔离身份(§3.11)、pre-push 闸、R5 / R8 / R9、`verify.ts` 四层、12.0 两份极详细的发版记录。本文把这些零件串成一条固定的线。

## 一、总模型:四道门

```
门 0 开发闸 ──→ 门 1 候选冻结 ──→ 门 2 候选验收 ──→ 门 3 正式制品 ──→ 门 4 分级放行与收口
(feat 内,已有)   (李哲定范围)      (local 版,按平台)   (静态 + 隔离冒烟)    (清单先、官网后)
```

| 门 | 谁签字 | 输入 | 输出 | 证据写在哪 |
|---|---|---|---|---|
| 0 开发闸 | feat 作者 + 李哲(合 main) | feat 分支 | 合进 main 且 status=done 的 feat | 各 feat 的三文档(不变) |
| 1 候选冻结 | **李哲** | 内容清单 | `release/<ver>` 分支 + 候选头 + 版本号 + `docs/features/release-<ver>/` | `release-<ver>/1-spec.md` |
| 2 候选验收 | 平台执行端(Mac = 笑南的电脑,Windows = Windows 电脑) | 候选头的 **local 版** | 两端验收回执全绿 | `release-<ver>/3-changelog.md` 验收节 |
| 3 正式制品 | 平台执行端 | 候选头 | 签名 / 公证后的制品 + 静态校验 + 隔离冒烟 | 同上,制品节(含 SHA-256) |
| 4 分级放行 | **李哲**(go / no-go、推 main、切官网) | 门 3 产物 | Release + 清单 + 观察期 + 官网 + tag + 台账 | `docs/installer-versions.md` + 交接单收口节 |

每道门**红了就退回上一道**,不带病过门。候选头一旦变化(哪怕一行),门 2 / 门 3 从头来。

## 三、门 1:候选冻结

1. **触发**:李哲说「发 `YYYY.次.补`」并给出内容清单。清单之外的任何东西不进包。
2. **只有 `status: done` 的 feat 进包**。in-progress 的 feat 要么在门 0 收口成 done,要么不进。这是 12.0 教训第 1 条,无例外。
3. **分支**:`release/<ver>` 从最新 main 切。若 main 上有不想带的内容(12.1 的情形),允许从上一 ship tag 切并 cherry-pick,但 1-spec 必须逐条列出带了什么、**没带什么**。
4. **版本号**:两端同号,用 `bump-installer-version.{sh,ps1}` 改 `installer-versions.json`,同时在 `docs/installer-versions.md` 建两条占位条目(macOS / Windows),哈希与链接留 `(to be filled)`。
5. **文档**:建 `docs/features/release-<ver>/`:
   - `1-spec.md`:内容表(feat-id / 来源 commit / 一句话)+ 验收标准(第四节清单的实例化,含**对照项**)+ 回退预案(第六节)。
   - `2-plan.md` 可省。
   - `3-changelog.md`:交接单 + 所有回执(第七节格式)。
   - INDEX 加一行 `release-<ver> | in-progress | … 交 <称呼>`。
6. **候选头** = 冻结时 `git rev-parse --short origin/release/<ver>`。所有制品、回执、台账都写它。
7. **冻结后改代码**只能走 `fix/<name>` 分支(从 `release/<ver>` 切)→ 分支内测试全绿 → `--no-ff` 合回 `release/<ver>` → 删 fix 分支 → 交接单第一节更新候选头,**已出的所有包作废重建**。禁止在 `release/<ver>` 上直接改代码。
8. **冻结后改文档**(交接、回执、台账)可直接提交到 `release/<ver>`。pre-push 闸对 docs-only 提交允许按 `.husky/pre-push` 头部说明跳过,但 commit message 必须写明原因;代码提交**永远不许**跳。

## 四、门 2:候选验收(local 版,按平台)

**口径(李哲 2026-11-09 确认)**:所有需要运行 DeskFox 的验证,用**同一候选头**构建的 `local` 本地版做(`-Env local`,独立 appId + `opencode-local.db`),与正在使用的正式版共存、互不打扰。正式制品不用于运行类验收(它的检查在门 3)。

每端各做一遍,结果按平台分段写进 `3-changelog.md`。清单如下,**每条写明命令 / 结果 / 执行电脑**:

**A. 自动化(在候选头上)**
- 完整 `.husky/pre-push` 闸全绿:fork 范围 typecheck + 六包单测(app / media-gen / adapter-feishu-lark / branding / desktop deskfox 子集 / session-ui)。工具链 bun 版本以根 `package.json` 的 `packageManager` 为准(当前 1.3.14;1.4.x 装依赖失败)。
- `bun run packages/branding/smoke/verify.ts --changed` 🟢,`--cold` 🟢(真冷 sidecar)。
- performance 组 `bun run --cwd packages/app test:bench` 全绿(规范 v8:进发版验收,不进 pre-push)。
- 触及 prompt / 上下文卡 / 选区 / 历史回填的版本,跑 `e2e/regression/context-card-flows.spec.ts`。

**B. 功能回归与行为对照(12.0 教训第 2 条,新增)**
- 1-spec 验收标准逐条勾选。
- **对照项**:本版触动过的每一条用户路径(拖放 / 附件 / 分享 / 供应商 / 更新提示 / 文件预览 …),与**上一正式版**的行为逐条对照;凡「与上一版不同」的,必须是 1-spec 写明的有意改动,否则按回归处理,退回门 1。对照用上一正式版的真实安装或其 local 包做,不靠记忆。
- **测试删改审计**:
  ```bash
  git diff --stat <上一 ship tag>..<候选头> -- '*.test.ts' '*.spec.ts' '*.test.tsx'
  ```
  被删除或断言被改写的每个测试,在交接单里一行解释「为什么不是回归」。解释不了的就是回归。

**C. 数据**
- 用真实库的**副本**(不是正式库)两次冷启动 + 旧会话续聊;记录迁移条数前后(如 38 → 39)、`PRAGMA integrity_check`、项目 / 会话 / 消息计数一致。
- 若本版含迁移,额外用上一正式版写过的库副本验一次升级路径。

**D. 真桌面 QA**
- native 项(对话框 / 通知 / 托盘 / Dock / 深链 / 文件关联 / IME / 路径)只认真桌面结果,按平台归属。
- 本人体验项由李哲做,Agent 不代替。

红了:在 `fix/<name>` 分支修,回到门 1 第 7 条。

## 五、门 3:正式制品

1. **构建环境**:从候选头在**独立打包环境**构建(独立工作树 + 独立输出目录,打包机上不运行正式版 DeskFox)。两端打包脚本会强制结束运行中的正式 / 预览 / Beta 版,这是设计(三档共享 `opencode.db`),不是 bug;所以不要在开着正式版干活的机器上打正式包。
2. **静态校验**(每端,写进交接单制品节):
   - 版本号、appId、Electron 版本、产物文件名与架构;
   - 载荷:LibreOffice 预设、插件、迁移条数、`app.asar` 与核验副本一致;
   - Mac:深签 + 公证 + staple,`spctl --assess` 通过;arm64 与 x64 各一份;
   - Windows:`bun run packages/branding/smoke/verify.ts --release --env prod` 🟢(latest.yml 的 SHA-512 与 exe 一致、版本非 0.0.0、blockmap、LO 进包);
   - 两端制品 SHA-256 与字节数写进 `docs/installer-versions.md` 对应条目。
3. **隔离冒烟**(2026-11-09 新增,是门 2 的 local 版验不到、只有正式包才有的几项):
   - ① 在**隔离账户或干净虚拟机**安装正式包,冷启动两次、正常退出;记录 Gatekeeper / SmartScreen 表现与首次启动是否有意外系统弹窗(钥匙串等)。
   - ② 用**上一正式版 + 真实库副本**做一次升级到候选(Windows:NSIS 覆盖安装;Mac:替换 .app 或应用内更新指向预发清单),启动后续聊;数据目录指向副本,绝不碰正式库。
   - ③ 做不到的项写明原因与豁免范围,**豁免由李哲签字**(12.0 先例:Intel 真机性能豁免)。
4. **Intel / x64**:必须出包、公证;至少在 Rosetta 下冷启动验证;Intel 真机不可用按第 3 条豁免。
5. 候选头变了 → 本节全部重做。

## 六、门 4:分级放行与收口

**顺序固定,每步回读后再做下一步**:

1. **上传制品**:GitHub Release(`ship-mac-prod-<ver>` / `ship-prod-<ver>`,latest 标)+ Gitee 镜像 + OSS CDN;逐个校验线上 digest 与本地一致。
2. **切更新清单**(`deploy-electron-updater.sh`):`latest-mac.yml`(四资产)/ `latest.yml`;Windows 还有旧 Tauri 迁移桥一并更新。切前**备份线上旧清单**,切后 HTTPS 回读 version 与 SHA-512。**此时只切清单,不切官网。**
3. **观察期**:至少一台装着上一正式版的团队设备收到更新提示、完成升级、冷启动续聊正常(这就是门 3 ② 之外的真实实包升级补验);自切清单起 **24 小时**内无阻断性反馈。观察期内发现阻断 → 把清单切回备份,走 hotfix(见回退预案),官网完全不动。
4. **切官网下载链接**(`deskfox-web` 仓两站四页 + 国内 CDN 链接),李哲确认后执行,回读六条链接 200。
5. **收口**:李哲确认 → `main` ff 合并 `release/<ver>` → 推 main → 推 tag;补 `chore(ship)` 台账提交(`docs/installer-versions.md` 两条填齐哈希 / 链接 / 回读结果;`release-<ver>` status 改 done;INDEX 同步);删 `release/<ver>` 与残留 fix 分支(tag 保留)。

**两端独立**:Mac 与 Windows 同号但各自过门,一端验收通过可先发,另一端不阻塞;各自切各自的清单与官网链接。

**回退预案**(门 1 时就写进 1-spec,切清单前复核):
- updater 禁降级(2026.12 起)意味着**用户装上后不能回退**;让用户降级会触发库隔离。所以回退只有两条路:① 观察期内 → 清单切回备份 + 官网不动;② 官网已切 → 官网切回上一版 + 立刻出 hotfix `YYYY.次.(补+1)` 走完整四道门。
- 预案里写明:上一正式版制品链接、清单备份位置、`deskfox-web` 回退 commit 的做法、本人正式库的恢复步骤(见 12.1 交接单第七节的六步)。

**台账只追加**:`docs/installer-versions.md` 与 `docs/features/release-*/`、`*-release-readiness/` 目录**从不删除已发布版本的条目**,哪怕该版本已回退。用树替换式合并建候选时,必须先把被替换掉的发布记录补回(12.1 教训)。

## 七、交接与回执(与三端协作指南第四节一致)

- **载体只有一个**:`docs/features/release-<ver>/3-changelog.md`。聊天 / 微信 / 飞书只做「去看某个文件」的通知。文档与代码同在 `release/<ver>` 分支(12.1 的 `release-handoff` 独立分支是过渡,见第九节)。
- **交接**五要素:接手人统一称呼 / 代码位置(分支 + 候选头)/ 已验到哪 / 剩下要做什么 / 怎么算验收。
- **回执**格式:`### 回执(<统一称呼>,YYYY-MM-DD)`,内容:做了什么、结果、commit、未做项、「待李哲」项。回执也是一笔 commit。
- **身份**:每条回执第一行写执行电脑;Git 作者不作身份依据(两台机器的作者配置都不是本人名字)。
- **对别人回执的更正**:直接追加新回执更正,不改别人写的段落。

## 八、硬规则速查(发版前对一遍)

1. 只有 `status: done` 的 feat 进包;清单之外不进。
2. 候选头写死;变一行就重验、重打、重签。
3. 冻结后改代码只走 `fix/<name>` → `--no-ff` 合回 `release/<ver>`;不在 release 分支直接改代码。
4. 运行类验收全部在候选头的 local 版上做;正式制品只做静态校验 + 隔离冒烟。
5. 每条被改动的用户路径都要与上一正式版对照;删改的测试逐条解释。
6. 数据验证只用副本,永不碰正式库。
7. 正式包在独立打包环境出;打包机上不跑正式版。
8. 放行顺序:制品 → 清单 → 观察 24 小时 → 官网 → main / tag / 台账。不许一步到位。
9. 切清单前回退预案写好并复核;updater 禁降级下回退 = 清单切回或 hotfix,不让用户降级。
10. 台账与发布记录只追加;代码推送永不 `--no-verify`,docs-only 跳闸须在 message 写明。
11. 回执写执行电脑,平台归属不交叉;需要李哲决定的标「待李哲」。
12. 本人体验项由李哲做;豁免由李哲签字。
